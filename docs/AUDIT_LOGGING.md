# 1. Purpose

This document defines the audit logging requirements for Purnata.

Purnata handles beneficiary information and operational records that must remain traceable. The PRD requires important actions to record, where appropriate:

- Who created a record
- Who modified a record
- When it was modified
- What type of action occurred

Auditability is especially important for beneficiary and program records. fileciteturn5file1L356-L367

The core principle is:

```text
Every Important Action Should Be Traceable
```

Important changes should have an identifiable user and timestamp. fileciteturn5file7L1325-L1355

---

# 2. Objectives

The audit system must provide:

1. Accountability.
2. Traceability.
3. Security visibility.
4. Operational history.
5. Support for investigating incorrect changes.
6. Evidence of important record modifications.
7. Visibility into relevant user actions.
8. Protection of sensitive beneficiary data.

Audit logging is not intended to replace normal application logging.

---

# 3. Audit Logging Principles

The implementation must follow these principles:

1. Important business actions must be traceable.
2. Audit records must be generated by the backend.
3. The authenticated user must be the source of actor identity.
4. Clients must not be allowed to forge `userId`/actor identity.
5. Audit records should be append-oriented.
6. Audit records should not be casually editable or deletable.
7. Audit logs must respect authorization.
8. Sensitive information must not be unnecessarily copied into logs.
9. Audit logging must not expose restricted beneficiary data.
10. Multi-step business operations should create audit records within the same transaction where appropriate.
11. Failed operations should not create misleading success audit records.
12. Audit definitions must remain synchronized with the Access Control Matrix and database schema.
13. Unresolved audit requirements must remain explicitly marked as open.

```text
                         User

                    /       \
                   /         \
                  ▼           ▼
```

The audit system belongs to the backend.

The frontend must never be responsible for creating authoritative audit records.

# 5. Audit Event Lifecycle

For an important successful operation:

```text
Request
   ↓
Authenticate User
   ↓
Authorize User
   ↓
Validate Request
   ↓
Execute Business Operation
   ↓
Create Audit Event
   ↓
Commit Transaction
   ↓
Return Success
```

For a failed transactional operation:

```text
BEGIN
 ↓
Business Operation
 ↓
Failure
 ↓
ROLLBACK
```

The system must not record a successful business-action audit event for an operation that was rolled back.

# 6. Audit Record Core Information

An audit record should identify, where applicable:

```text
actor/user
action
entity/resource type
entity/resource ID
description
timestamp
metadata
```

The existing architecture and database design identify audit records as part of the system's traceability model.

# 7. Recommended Audit Log Structure

The logical audit record is:

```text
AuditLog
├── id
├── userId
├── action
├── entityType
├── entityId
├── description
├── timestamp
└── metadata
```

The exact PostgreSQL column names and types must remain consistent with `DATABASE_SCHEMA.md`.

---

# 8. Audit Log ID

The audit record should use the PostgreSQL UUID strategy defined for the platform.

Conceptually:

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

The ID is an internal technical identifier.

It must not be supplied by a normal client request.

---

# 9. Actor / User ID

`userId` identifies the authenticated user who caused the auditable action.

Rules:

- Derive from authenticated request context.
- Never trust a client-supplied actor ID.
- Must reference an existing user where the schema requires it.
- Must remain associated with the audit event.

Example:

```text
Authenticated User
      ↓
request.user.id
      ↓
audit_logs.user_id
```

---

# 10. Action

`action` describes what happened.

The value must use the approved `AuditAction` enum defined by the data model.

The backend must reject or prevent arbitrary action names from being inserted into authoritative audit records.

---

# 11. Entity Type

`entityType` identifies the resource affected by the action.

Examples may include:

```text
USER
CENTRE
BENEFICIARY
PROGRAM
PROGRAM_ENROLLMENT
ACTIVITY
ATTENDANCE
VOLUNTEER
VOLUNTEER_ASSIGNMENT
TASK
PROGRESS_RECORD
TIMELINE_EVENT
```

Only entity types supported by the approved schema should be implemented.

---

# 12. Entity ID

`entityId` identifies the affected record.

Examples:

```text
program UUID
beneficiary UUID
activity UUID
task UUID
```

If an operation affects a collection or does not have one resource ID, the representation must follow the finalized API/database contract.

Do not invent a fake entity ID.

---

# 13. Description

The description provides a human-readable summary.

Examples:

```text
Beneficiary registered
Program created
Volunteer assigned to program
Attendance recorded
Progress record updated
Task completed
```

Descriptions must not contain unnecessary sensitive beneficiary information.

Prefer:

```text
Beneficiary record updated
```

over copying the entire beneficiary profile into the audit log.

---

# 14. Timestamp

Every audit event must have a timestamp.

The timestamp should be generated by the backend/database rather than trusted from the client.

Use the platform's consistent timestamp strategy.

Conceptually:

```text
created_at / timestamp
```

The exact column name follows the database schema.

---

# 15. Metadata

Metadata may contain structured context useful for auditing.

Possible metadata:

```json
{
  "changedFields": ["status", "description"],
  "previousStatus": "ACTIVE",
  "newStatus": "COMPLETED"
}
```

Metadata must be used carefully.

Do not store sensitive personal information unless it is explicitly required and approved.

# 31. Authentication and Security Events

Authentication-related events may include:



---

# 32. Authorization Failure Logging

The API returns an authorization error for unauthorized operations, conceptually:

```http
403 Forbidden
```

The Access Control Matrix requires unauthorized access to be rejected without revealing sensitive information. fileciteturn5file0L15-L37

Whether every `403` is persisted as an audit event is an open policy decision.

If implemented, the audit event should contain enough information for investigation without revealing restricted resource data.

---

# 33. Successful vs Failed Actions

Audit semantics must distinguish:

```text
successful business action
```

from:

```text
attempted action
```

Example:

```text
Beneficiary update succeeds
→ UPDATE audit event

Beneficiary update rejected by validation
→ no successful UPDATE event
```

If security policy requires logging the failed attempt, use a separate action/event category.

---

# 34. Transactional Audit Logging

When a business operation modifies multiple tables, audit creation should normally be part of the same transaction.

Example:

```text
BEGIN
  ↓
Create Enrollment
  ↓
Create Timeline Event
  ↓
Create Audit Log
  ↓
COMMIT
```

If the enrollment rolls back:

```text
ROLLBACK
```

the corresponding successful audit event must also roll back.

# 39. Sensitive Data Rules

Beneficiary information may contain sensitive personal information.

The PRD requires minimum necessary access and auditable data access. fileciteturn5file1L371-L383

Therefore audit metadata must follow:

```text
Minimum Necessary Data
```

Do not store:

```text
passwords
password hashes
authentication tokens
session secrets
unnecessary personal details
full beneficiary profiles
```

# 40. Authentication Credential Protection

Audit logs must never contain:

```text
plain-text passwords
password hashes
access tokens
refresh tokens
session secrets
database credentials
API keys
```

These values are not audit evidence and create additional security risk.

# 41. Audit Log Immutability

Audit records should be treated as append-oriented historical records.

Normal application users must not be able to:

```text
UPDATE audit logs
DELETE audit logs
```

The final database role/administrative policy must enforce this.


# 50. Audit Log Ordering

Audit logs should normally be ordered by:

```text
timestamp DESC
```

so the most recent events appear first.

The API should use a deterministic secondary ordering where necessary.

---

Because audit logs are historical and potentially large, indexes should support common authorized queries.


The final indexes must be based on the actual `DATABASE_SCHEMA.md` and observed query patterns.

# 54. Audit and Backups

Audit logs should be included in the database backup strategy because they are part of historical traceability.

The production backup and recovery policy is still an open technical decision.

---

# 55. Audit and Database Transactions

Audit records for successful business operations should be transactionally consistent with the operation whenever possible.

Example:

```text
Program Update
   +
Audit Log
```

must not produce:

```text
Program update committed
Audit missing
```

because the audit write failed silently.

The service should handle audit-write failures according to the finalized reliability policy.

---

# 56. Audit Failure Policy

For important operations, the project must decide whether:

```text
audit failure
    ↓
rollback business operation
```

or:

```text
business operation succeeds
audit failure is handled separately
```

For the MVP, transactional audit logging is recommended for critical multi-table business operations.

However, the final policy should be explicitly approved rather than silently assumed.

# 61. Audit Middleware vs Service

Do not rely only on generic HTTP middleware for business audit events.

Why?

A generic middleware can know:

```text
HTTP method
URL
user
```

but may not know:

```text
what business entity was actually changed
whether the transaction committed
what status changed
whether the operation succeeded
```

Therefore:

```text
Business Audit Events → Service Layer
```

Generic security/request logging can remain middleware-level.

---

# 62. Audit vs Application Logs

These are different:

| Application Log | Audit Log |
|---|---|
| Technical diagnosis | Accountability |
| Debugging | Historical traceability |
| Errors/exceptions | Business/system actions |
| May be verbose | Should be structured |
| Not necessarily user-visible | May be authorized for viewing |
| Operational infrastructure | Persistent business history |

Do not use ordinary console/application logs as a replacement for audit records.


# 64. Audit and Authorization

Audit logging must never bypass authorization.

Example:

```text
Volunteer
   ↓
Own Audit Logs
```

does not imply:

```text
Volunteer
   ↓
All Audit Logs
```

Likewise, a Program Lead's access to a program does not automatically grant access to all audit logs in the system.

# 81. Performance Considerations

Audit logging should not unnecessarily slow normal workflows.

Recommended:

```text
structured insert
indexed timestamp
indexed actor/entity where needed
transactional write for critical operations
minimal metadata
```

Avoid storing unnecessarily large JSON objects in every audit event.

# 89. Final Audit Principle

Purnata follows:

```text
IMPORTANT ACTION
      ↓
IDENTIFIABLE USER
      ↓
IDENTIFIABLE RESOURCE
      ↓
ACTION TYPE
      ↓
TIMESTAMP
      ↓
TRACEABLE HISTORY
```

while preserving:

```text
Minimum Necessary Access
        +
Sensitive Data Protection
        +
Role + Scope Authorization
        +
Database Integrity
```

The audit system should make important changes accountable without turning audit logs into a second copy of the entire beneficiary database.

The final implementation must remain consistent with the project's source-of-truth hierarchy:

```text
Stakeholder Decision
        ↓
Approved PRD
        ↓
Approved API / Data / Architecture Documents
        ↓
Approved UI Specifications
        ↓
Existing Implementation
        ↓
Developer Assumptions
```

When an important audit requirement is ambiguous, the implementation must seek clarification rather than inventing behavior. fileciteturn5file7L1359-L1377
